# /update-ext

Команда для релизного workflow проекта `remanga-ext`.

## Цель

Синхронно обновить:
- версию в `package.json`
- changelog в `build.js`
- публичную документацию только там, где это действительно требуется
- собранные артефакты через `npm run build`

Не придумывай изменения сам. Если входных данных не хватает, сначала задай уточняющие вопросы.

## Вход

Поддерживай такие варианты:

```text
/update-ext patch Заголовок релиза; - Изменение 1; - Изменение 2
/update-ext minor Новый блок функциональности; - Добавлено ...
/update-ext major Большой релиз; - Удалено ...
/update-ext 1.7.0 Заголовок релиза; - Изменение 1; - Изменение 2
```

### Правила разбора

1. Первый аргумент — либо `patch`, `minor`, `major`, либо явная версия `x.y.z`.
2. Остальной текст — данные для changelog.
3. Предпочтительный формат changelog-данных:
   - первая часть до `;` — заголовок релиза
   - остальные части `; - ...` или отдельные `- ...` — bullets изменений
4. Если bullets не переданы, не выдумывай их. Спроси пользователя.
5. Если bump/version не передан, не гадай. Спроси пользователя.

## Источники правды

Всегда опирайся на эти файлы:
- `package.json` — текущая версия
- `build.js` — userscript header и основной changelog
- `README.md` — публичные возможности/использование/установка
- `docs/ROADMAP.md` — completed roadmap items с `✅ vX.Y.Z`
- `docs/*.md` — менять точечно, только если там уже есть релевантное описание feature или release-пункта

Не обновляй `dist/*` вручную, кроме результата `npm run build`.

## Workflow

### 1. Подготовка

1. Создай/обнови task list.
2. Прочитай:
   - `package.json`
   - `build.js`
   - `README.md`
   - `docs/ROADMAP.md`
3. При необходимости найди релевантные docs через `Grep` по ключевым словам из описания изменений.

### 2. Вычисление версии

Прочитай текущую версию из `package.json`.

Если аргумент:
- `patch` → `x.y.(z+1)`
- `minor` → `x.(y+1).0`
- `major` → `(x+1).0.0`
- `x.y.z` → проверь regex `^\d+\.\d+\.\d+$`

Потом обязательно проверь:
- новая версия валидна
- новая версия строго больше текущей

Если версия невалидна или не больше текущей — остановись и объясни проблему.

### 3. Построение changelog entry

Новый entry всегда вставляй в начало CHANGELOG-блока в `build.js` в текущем формате:

```text
 * vX.Y.Z - Заголовок
 * - Изменение 1
 * - Изменение 2
```

Правила:
- newest first
- существующие записи не переписывай без причины
- regex и функции `extractChangelogVersions()` / `syncLandingChangelog()` не меняй, если нет явной поломки
- заголовок и bullets бери только из ввода пользователя или из явного подтвержденного контекста

### 4. Решение по документации

Обновляй docs только по необходимости.

#### Обновить `README.md`, если:
- появилась новая пользовательская функция
- изменился UX/использование
- изменилась установка/обновление
- изменилось описание возможностей
- изменились важные детали безопасности/архитектуры, видимые пользователю

#### Обновить `docs/ROADMAP.md`, если:
- релиз закрывает один из существующих пунктов roadmap
- можно точно сопоставить изменение с конкретным пунктом

Формат roadmap:
```text
~~текст пункта~~ ✅ vX.Y.Z
```

#### Обновить другой файл в `docs/`, если:
- в нем уже есть planned/report/reference блок про ту же функцию
- без этого документ станет противоречить текущему релизу

#### Не обновлять docs, если:
- изменения внутренние
- багфикс не меняет публичное поведение
- нет очевидного релевантного документа

В этом случае явно напиши пользователю, что docs пропущены намеренно.

### 5. Перед правками покажи план

До любых `Edit`/`Write` кратко сообщи пользователю:
- текущую версию
- новую версию
- заголовок релиза
- bullets changelog
- какие файлы будут изменены
- какие docs будут обновлены или пропущены и почему

Если вход был неполным или решение по docs неоднозначно — используй `AskUserQuestion`.

Если пользователь уже явно попросил выполнить обновление без дополнительного подтверждения, можно продолжать. Если нет — запроси короткое подтверждение перед правками.

### 6. Применение

После подтверждения:
1. Обнови `package.json`
2. Обнови CHANGELOG-блок в `build.js`
3. Обнови только релевантные docs
4. Не трогай лишние файлы

Предпочитай `Edit`. `Write` используй только если создаешь новый файл, который действительно нужен для команды.

### 7. Проверка

После правок обязательно:

1. Запусти:
```bash
npm run build
```

2. Проверь результат:
- `dist/remanga-extension.user.js` содержит новую `@version`
- `dist/remanga-extension.user.js` содержит новый changelog entry
- `dist/script.js` содержит новый entry в `CHANGELOG_DATA`

3. Если менялся `README.md` или `docs/*`, перечитай измененные участки и убедись, что текст согласован с релизом.

### 8. Финальный отчет

Сообщи кратко:
- какая версия была и какая стала
- какие файлы изменены
- какие docs обновлены
- какие docs намеренно не тронуты
- прошла ли сборка

## Ограничения

- Не придумывай release notes без данных пользователя.
- Не меняй `dist/*` вручную.
- Не создавай новые markdown-документы без явной необходимости.
- Не обновляй unrelated docs.
- Не делай commit/push без прямой просьбы пользователя.

## Минимальные уточняющие вопросы

Если вход неполный, спроси максимум нужное:
1. Какой bump нужен: `patch`, `minor`, `major` или точная версия?
2. Какой заголовок релиза?
3. Какие ключевые изменения войдут в changelog bullets?
4. Закрывает ли релиз конкретный пункт в `docs/ROADMAP.md`?
